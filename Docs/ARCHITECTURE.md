# GO 3S 手语翻译 — Android 架构设计

> **状态：修订稿，待模型与实机验证** | 最后更新：2026-09-22
> 本文规定实现方案，不代表软件已实现或性能已达标。队列容量、超时和验收目标中的初始值须通过目标手机验证。

---

## 1. 系统概览

### 1.1 已确定的产品边界

- 相机画面只交给算法或 PC 训练程序，**不提供面向人的视频预览界面**；手机仍显示字幕、连接状态、错误和操作按钮。取景确认使用 Insta360 官方配套 App 完成，本 App 不重复实现预览（此决策已确认，替代原始需求中的 App 内实时预览）。
- GO 3S 作为 Wi-Fi 热点，手机连接该热点接收相机编码数据。BLE 仅用于发现设备和读取热点信息，不传输视频。
- SDK 将实时取流接口命名为 `CameraPreview` / `startStream()`。这里的“预览流”是相机提供的数据通道，**使用它不等于在屏幕上显示画面**。
- 成品在手机上进行手语识别；本地语言处理为默认方案，云端文本处理仅在用户主动启用且网络可用时使用。
- 用户选择字幕输出语言和语音语言。默认仅中文；仅选择中文时不调用其他语言翻译，不要求中文必须和其他语言一起显示或播报。
- 模型的采样率、输入尺寸、序列长度、预处理和推理引擎由后续训练结果决定，不预先固定为 5fps。
- **支持连续表达，不提供“完成本句”按钮，不要求用户逐句点击或等待系统处理后再表达。** 自动判断表达边界是连续翻译的发布门槛；异常文本核对是可选纠错，不是正常使用的必经步骤。
- 句子长度、大模型输入预算及拆分/合并策略先预留设计位置，后续依据模型能力与实测确定，不预先规定用户每次只能表达多少秒或多少字。
- 训练版与成品版分开构建、分开安装。成品不包含训练采集接口，不保存视频、截图或图像帧；训练素材经明确允许后保存到 PC。

### 1.2 数据流

```text
GO 3S Wi-Fi 热点
    │ H.264 / H.265 编码数据
    ▼
Camera Link：BLE 配网 → 手机连相机 Wi-Fi → SDK 收流
    ▼
有界编码队列 → 同帧分片聚合 → 参数集与关键帧准备
    ▼
MediaCodec：无显示 Surface 的解码 → 可读 YUV 图像
    ▼
像素布局读取、裁剪与方向处理 → 按输出端契约转换
    ├─ 训练版：帧 + 时间戳 + 元数据 → USB / ADB forward → PC 采集与训练
    └─ 成品版：模型所需采样、预处理与序列组装
                  ▼
              手语模型：动作内容、时间范围 → 经验证的自动边界判断
                  ▼
              App 句子管理：持续接收新动作，各段独立收尾 / 确认 / 标疑 / 中断
                  ▼
              LLM：受限中文整理 → 仅翻译用户选择的语言
                  ▼
              按句子和语言更新字幕 → App TTS 队列播报
```

不设置 TextureView、SurfaceView、预览播放器或双路渲染；不为获取模型像素而再次编码视频。训练版的数据通道与成品版的识别输出互斥，不在成品运行中偷偷启动采集。

### 1.3 运行与构建模式

| 项目 | 训练版 `training` | 成品版 `production` |
|---|---|---|
| 目的 | PC 数据采集、训练及联调 | 手机本地识别与翻译 |
| 共用部分 | Camera Link、分片聚合、解码、基础像素转换 | 同左 |
| 视频画面展示 | 不提供 | 不提供 |
| 输出 | USB 上的帧与元数据 | 用户选择语言的字幕与 TTS |
| 手机帧落盘 | 不提供；传输只使用内存 | 不允许 |
| PC 素材保存 | 明确开启采集、取得授权后允许 | 不存在该能力 |
| USB Bridge | 仅训练构建包含 | 源码、服务入口和采集依赖不打包 |
| 包名与数据目录 | 独立包名，带 `.training` 后缀 | 正式包名，与训练版隔离 |
| 安装提示 | 明确标识“训练采集版” | 无训练开关或采集入口 |

## 2. 模块设计

### 2.1 Camera Link — 相机连接、权限与生命周期

#### 2.1.1 接入与初始化

使用 Insta360 Camera SDK 2.x；实际依赖版本须从已获授权的 SDK/Demo 确认并锁定，不将 `2.x.x` 当作可构建版本。无播放器需求时不主动引入 Media SDK；若具体 Camera SDK 的依赖或初始化契约要求它，再按官方包补入。

初始化顺序：

1. `Application.onCreate()` 初始化 SDK；仅初始化，不在此直接扫描或弹权限请求。官方 Demo 2.1.5 的实际位置是 MainActivity 运行时权限授予后调用 `InstaCameraSDK.init`（cacheDir 指向 externalCacheDir）；两种位置均为官方样例，本项目先按 Application 位置实现，首个真机构建时验证等价。
2. 用户点击“开始”，检查当前系统版本所需权限、蓝牙/Wi-Fi 状态及运行模式。
3. 从可见 Activity 启动前台会话服务；BLE 扫描，用户选择设备并连接。
4. 确认相机 Wi-Fi 处于 AP 模式：Demo 先 `fetchWifiData()` 检查 `mode`，不是 AP 时 `setWifiMode(AP, "")` 并轮询至多约 5 秒。随后通过 `system.getWifiData()` 读取相机热点信息；不要在日志中打印 SSID 密码。
5. 手机通过系统 Wi-Fi 流程连接相机热点，等待网络可用回调，再调用 `bindProcessToNetwork(network)` 并检查返回值。
6. 释放 BLE 控制通道：Demo 直接调用 `bleCamera.release()`（内部已含断连语义，无需再调 `disconnect()`），获取 Wi-Fi `CameraDevice`，调用 `connect(network.networkHandle)`。
7. 注册并等待授权状态：已授权继续；未授权等待相机上的允许操作；拒绝、超时或 `SYSTEM_BUSY` 显示具体状态，不直接进入取流。
8. 如相机尚未激活，完成 `system.activeCamera(appId, secretKey)` 所需流程；激活失败则停止本次启动。凭据不提交到仓库，不写入日志。Demo 证实激活需访问公网 `openapi.insta360.com`（绑网状态下以临时解绑/恢复的 `runOnDefaultNetwork` 包装执行），因此激活必须在手机可上网时完成；纯相机热点绑网状态下激活会因 DNS 失败而不可用，离线首次使用前须完成激活。
9. 执行并检查 `capture.loadJson()`，再查询机型能力、编码类型及可用采集参数；不可把录像分辨率当作预览流分辨率。
10. 注册断连、电量、温度和 `CameraStreamListener`。调用 `device.preview.init(application)`（Demo 2.1.5 实测必需步骤）后调用 `startStream()`。
11. 接收 `onParamsChanged` 的实际宽、高、帧率及参数信息，准备解码；流打开后请求关键帧。参数集和可用随机访问帧齐备才开始有效出图。

> SDK 2.1.5 另提供 `ConnectType.WIFI_AWARE`（Wi-Fi Aware / NAN）路径：BLE 引导相机进入 Aware 模式 → NAN 握手 → `connectWiFiAware(networkHandle, peerIpv6)`，无需手机连接相机热点。本方案仍以热点 Wi-Fi 为主路径；Aware 网络同样不带互联网（Demo 的 `runOnDefaultNetwork` 注释证实绑定时 DNS 解析失败），其稳定性与适用性列入真机评估项，不改变云端请求的网络设计。

#### 2.1.2 权限与系统版本

以下是实施检查表；Manifest 声明、运行时申请和用户拒绝处理必须对应实际调用的 API，不申请无关权限。

| 场景 | 要求 |
|---|---|
| 基础网络 | 声明 `INTERNET`、`ACCESS_NETWORK_STATE`；按 Wi-Fi/网络请求 API 声明 `ACCESS_WIFI_STATE`、`CHANGE_WIFI_STATE`、`CHANGE_NETWORK_STATE` |
| Android 9–11 BLE 扫描 | 兼顾旧版蓝牙权限和扫描所需的位置权限/系统设置 |
| Android 12+ BLE | 按操作请求 `BLUETOOTH_SCAN`、`BLUETOOTH_CONNECT`；只有满足不推导位置的条件才声明 `neverForLocation` |
| Android 13+ Wi-Fi | 相关管理 API 请求 `NEARBY_WIFI_DEVICES`；`startScan/getScanResults` 等仍按官方要求处理精确位置权限，不能一概豁免 |
| Wi-Fi 连接差异 | Android 10+ 使用适合应用连接设备热点的系统流程并等待用户批准；Android 9 单独适配，不能假设新 API 可用 |
| 前台服务 | 声明 `FOREGROUND_SERVICE`、`FOREGROUND_SERVICE_CONNECTED_DEVICE` 和 `foregroundServiceType="connectedDevice"`，满足该类型的实际前置条件 |
| 通知 | Android 13+ 处理 `POST_NOTIFICATIONS`；拒绝通知不等同于系统禁止所有前台服务，但 App 必须解释影响，服务仍需提供规定的通知 |
| 震动 | 声明 `VIBRATE`；遵守系统设置，不通过额外权限绕过勿扰 |

用户拒绝或撤回权限时停止相应操作，显示原因和重试/前往设置入口；不循环弹窗。开始前检查模型文件和所选语言的离线语音准备情况，缺项时分别提示，不能以“相机已连接”代替整个会话就绪。

#### 2.1.3 状态与清理

```text
IDLE → CHECKING → BLE_CONNECTING → WIFI_CONNECTING
     → AUTHORIZING → ACTIVATING（必要时）→ PREPARING → STREAMING

连接丢失 → RECONNECTING → 重新执行网络、授权及准备步骤
权限拒绝 / 用户停止 → STOPPING → IDLE
相机过热 → PAUSED_HOT → 冷却且用户确认后重新开始
不可恢复错误 / 重试耗尽 → ERROR → 用户重试
```

- 会话由前台服务持有；ViewModel 只订阅状态和发送命令，页面重建不重复开流。
- 前台服务不是永不被杀保证。进程被杀后，下次启动显示会话已中断，不自动重播之前未完成的语音。
- 非主动断连采用 1、2、4、8、16 秒退避，最多 5 次；通知立即显示中断，全部失败后才触发连接失败震动。成功重新出图后清零重试次数。
- 用户停止、权限拒绝、过热不进入普通断线重试；用户停止优先于任何延迟重试任务。
- 每次重新连接或重建解码链增加 `streamGeneration`（数据代次）。旧代次的帧、识别和语言处理回调不能再更新当前句子。
- 连接断开时中断未确认句子；已确认且正在播报的内容可播完，但清空尚未开始的自动播报，字幕标注未播报。新数据不能拼到旧草稿上。
- 正常退出顺序：进入 STOPPING、禁止新任务并使迟到结果失效 → 取消重试，立即停止 TTS 播报与排队 → 停流并注销 SDK 监听，关闭训练监听，训练连接按 §2.8.2 有限收尾后关闭（异常立即关闭以解除阻塞）→ 关闭任务入口，取消聚合、解码、预处理、手语推理、语言处理及网络任务 → 等待所有实际资源使用者退出 → 释放缓冲、解码器、手语模型、语言模型与 TTS 引擎 → 断开设备 → 解除进程绑网 → 注销 Wi-Fi/蜂窝网络请求 → 停前台服务。
- “等待退出”是资源释放屏障：不仅等待协程 `cancelAndJoin()`，还要确认原生推理、GPU 工作及在途回调已经停止访问资源。包装协程被取消不等于原生调用已返回；不可取消的调用返回前保留其输入和模型，返回后丢弃结果，再按后端规定的线程/上下文释放。不得在主线程阻塞等待，也不得在旧实例未退出时启动重叠会话。
- 清理等待设置后端实测的有限告警时限；超时显示清理异常，继续清理无依赖的网络等资源，但不能因超时强行释放仍被访问的对象。仍在执行的任务保留退出后释放责任，无法恢复时提示重启 App，不假装已回到 IDLE。解绑必须调用 `bindProcessToNetwork(null)`；异常路径采用同一套幂等清理，单个系统调用失败不跳过其他可安全执行的清理。
- 切后台或锁屏时，由已启动的前台服务继续会话；回到前台重新核对连接、权限、模型与网络状态，不创建第二份会话。

### 2.2 Video Processor — 分片聚合、解码与格式转换

#### 2.2.1 分片聚合规则

SDK 附件中 `PreviewStreamFrame` 包含 `data`、`timestamp`、`type`；本设计不依赖额外的“末包”字段。官方说明同一帧的分片共享 timestamp，示例以 timestamp 变化提交上一帧。

实施规则：

1. 回调中只过滤视频类型、记录接收时间、取得受容量限制的数据所有权并投递；不做解码、图像转换或阻塞等待。
2. SDK 未明确字节数组生命周期前，采用有界复制，避免回调结束后 SDK 复用数组；确认 SDK 契约后才能优化复制。
3. 按所选视频流及数据代次维护当前 timestamp 的聚合缓冲；不混合不同流或重连前后的数据。
4. 在确认回调保持同帧连续交付的前提下，以 timestamp 切换结束上一帧。此规则来自 SDK 示例，不足以证明网络未丢片；实际回调顺序和数据完整性仍是验收项。
5. 停流、异常、超时后的尾部缓冲不能仅因“等了一会儿”就当成完整帧提交；未确认完整的尾帧丢弃。
6. 发现队列溢出、可检测的异常顺序、非法码流或聚合超限，进入重新同步：清空受影响的编码积压和解码状态，请求新关键帧，并使下游未确认序列失效。
7. 若实际 SDK 的顺序契约不能支撑上述完成判断，必须补充经验证的完整帧边界解析或取得官方接口说明，不能用猜测补包后发布。

NAL 是视频编码中的数据单元，不一定等于一帧。先确认码流是 Annex-B 起始码还是长度前缀封装，再解析单元；不只识别四字节起始码，也不把某个起始码当作完整帧结束标记。

#### 2.2.2 解码启动与恢复检查表

| 步骤 | 处理 | 未满足时 |
|---|---|---|
| 确认编码 | 查询 `fetchVideoEncodeType()`，明确 H.264 / H.265 | 查询失败不能直接默认为 H.264；经已验证的参数集解析确认或报错 |
| 取得格式 | 获取实际宽、高和必要编码配置 | 等待参数，不用录像规格或固定 4K 值代替 |
| 准备参数集 | H.264 使用 SPS/PPS，H.265 使用 VPS/SPS/PPS；按 MediaCodec 要求组织 CSD 或带内配置数据 | 继续等配置或请求重发；不直接投喂任意中间帧 |
| 创建解码器 | 核查目标设备对编码、分辨率、帧率及可读输出模式的支持，`configure` 不传显示 Surface | 提示当前规格/设备不支持；只切换相机实际支持且模型验证过的规格 |
| 等待同步起点 | 请求并识别可用随机访问关键帧，如 H.264 IDR；H.265 按对应随机访问规则处理 | 不把任意标成 I 帧的数据都视为可立即恢复的起点 |
| 正常出图 | 根据输出格式读取有效图像并及时释放 codec 缓冲 | 格式不可读则报告不兼容，不猜布局 |
| 参数改变/断流恢复 | 清空未确认时序数据，重新取得配置并重建解码器 | 不复用旧宽高、旧参数集或旧识别草稿 |

相机 timestamp 与手机时间不是天然同一个时钟。SDK 示例将毫秒转为 MediaCodec 所需微秒，接入具体版本时核验单位；模型输入保留媒体时间，排队和超时使用手机单调时钟，历史记录另存墙上时间。不能直接拿相机 timestamp 当作 Unix 时间。

#### 2.2.3 只解码，不为模型重新编码

```text
压缩视频 H.264/H.265
    → MediaCodec 解码（无显示 Surface）
    → getOutputImage(index) 的可读图像
    → 按 planes / rowStride / pixelStride / cropRect 读取有效像素
    → 统一方向、裁剪、颜色布局，按模型要求缩放与归一化
    → 模型输入张量
```

- 请求 `COLOR_FormatYUV420Flexible` 并验证实际输出能力，它是一类可变布局的 YUV420，不承诺 NV12。
- 优先通过 `Image` 读取各平面；只在具体解码器输出契约已确认时使用原始 ByteBuffer 布局。不能读取的设备暂列不兼容，不在此引入显示渲染来假装解决。
- 模型要 RGB 就转换成 RGB；需要紧凑 I420/NV12 才做对应像素重排。**像素格式转换不是 H.264/JPEG 重新压缩编码**，后者会增加耗时或损失图像信息。
- libyuv 等只对匹配布局的输入使用相应转换函数；处理实际裁剪、方向、行填充以及色彩范围，不直接将整个缓冲视为紧密排列图像。
- 输出 Image/ByteBuffer 由解码器持有，必须在 `releaseOutputBuffer(index, false)` 前完成读取或复制。跨协程只传应用拥有的像素/张量，不传已释放 codec 缓冲的引用。
- 不采样的解码输出立即释放。为保持参考帧依赖，不能先按模型帧率随意丢弃编码 P/B 帧；采样发生在解码之后。

#### 2.2.4 采样与预处理契约

最终模型随包提供 `ModelSpec`（输入说明），至少包含：

| 字段 | 含义 |
|---|---|
| 模型/预处理版本、校验值 | 保证 PC 训练与手机使用同一套规则 |
| 输入类型 | RGB 视频、关键点或模型指定组合 |
| 输入宽高、颜色顺序、张量维度顺序 | 如 RGB/BGR、通道在前或在后 |
| 数据类型及数值范围 | Float/量化整数、归一化参数 |
| `inputFps`、`sequenceLength`、`windowStride` | 采样频率、一个窗口需要的帧数、窗口前进步长 |
| `maxFrameGap` 与缺帧规则 | 多大的采样间隔可接受，是否允许特定重采样 |
| 裁剪、方向、镜像、去噪规则 | 与训练一致，不能手机端临时增删处理 |
| 输出与时序解码方式 | 标签/词序列/句子、时间区间、状态缓存、稳定内容提交与跨边界对齐方式 |
| 自动边界契约 | 模型自带边界信号或配套边界模块、媒体截止点、所需后续上下文和边界可靠性规则；必须支持不停流接收后续表达 |
| 置信度与拒识阈值 | 从验证集校准，不能将任意分数直接当成准确率 |
| 推理后端与资源需求 | 实测支持的 CPU/GPU 等运行配置、内存与加载方式 |

训练完成前不锁定上述值，尤其不固定 5fps 或按 I 帧采样；尚无经验证的自动边界与连续处理能力时，不发布连续翻译，也不以逐句操作替代该能力。训练采集使用单独记录版本的 `CaptureSpec`，在相机和 USB 吞吐允许下保存连续样本与真实时间戳，后续在 PC 比较不同模型采样方案。

#### 2.2.5 有界队列与过载规定

以下为第一轮实现的保护性初始值，不是吞吐保证，也不是不可调整的产品上限；以目标模型和真机压测修改并记录，不静默扩大到无界缓存。实时识别优先控制数据年龄，训练传输优先吸收短时抖动：前者不能靠积压数秒旧画面保持表面流畅，后者采用 §2.8.2 的独立大缓冲，不受下表“待转换 2 帧”的限制。

| 位置 | 初始容量/时限 | 超限处理 |
|---|---|---|
| SDK 编码分片入口 | 最多 128 个分片且合计不超过 8 MiB；最老数据排队不超过 250ms | 回调只报告一次过载事件并阻止继续积压；工作线程清空旧编码数据、重建同步状态并请求关键帧 |
| 当前帧聚合 | 单帧不超过 4 MiB，同 timestamp 等待不超过 500ms | 丢弃未确认完整的数据并重新同步；若合法关键帧超限，测量后调整上限，不能截断 |
| 完整编码帧待解码 | 最多 4 帧且合计不超过 8 MiB，排队不超过 250ms | 不任意丢中间参考帧；清空受影响解码链后重新同步 |
| 待转换的原始解码图像 | 应用最多持有 2 帧，处理后立即归还缓冲池 | 能按模型采样契约跳过则释放；丢失必需采样则向序列组装器发送缺帧事件 |
| 模型采样帧/在途张量 | 环形采样区按 `sequenceLength + 2` 规划；所有保留帧和在途窗口张量合计初始上限 64 MiB | 启动前检查规格能否装下，装不下拒绝启动该规格；不偷改模型输入尺寸 |
| 模型推理 | 1 个执行中的窗口 + 最多 1 个待执行窗口 | 不静默覆盖未处理动作；过载导致整段未确认序列中断，清空待执行序列并提示，按新序列重新开始 |
| 语言处理 | 1 个执行中的句子 + 最多 2 个待处理句子 | 超出预算转明确的未处理/降级状态，保留确认文本，不无限排队、不悄悄漏句 |

额外约束：

- 不忽略 `trySend()` 的失败结果；关闭 Channel、取消任务和异常路径均归还未被使用的缓冲。在途缓冲必须等最后一个实际使用者退出后再归还，不能在协程取消时提前释放原生调用仍在读取的输入；停止与解码重建均遵守 §2.1.3 的资源释放屏障。
- 编码丢失重置解码链；模型输入缺帧通常只重置受影响的识别时序状态，不无故重启相机。
- 新的 `sequenceEpoch`（识别序列代次）使旧推理结果失效。某些推理调用不能立即取消时，等其返回后丢弃旧结果，不启动并发解释器争用同一实例。
- 模型窗口应按媒体时间连续组装；超过 `maxFrameGap` 就中断该段，只有训练契约明确支持才做插值、重复帧等补偿。
- 保留窗口引用的帧不得被环形缓冲覆盖；不可变窗口及其所有权计入内存上限。
- 连续过载提示“当前设备/配置处理不足”，暂停识别并引导换已验证配置，不自动改采样率后继续假装正常。
- 手机总内存预算还包括解码器内部缓冲、模型权重、运行时和 LLM，64 MiB 仅约束上述帧/张量池，不代表应用总内存。若 ModelSpec 确需更大的帧池，可在测量整体峰值内存后提高该预算；不因帧池扩大而自动增加推理排队时间。
- 缓存只能吸收短时速度波动；长期输入速度高于处理或发送速度时，再大的有限缓存也会填满。调整容量必须同时检查帧数、字节数、最老数据年龄和持续吞吐，不能只看手机标称内存。

### 2.3 Post-Processing — 模型处理管线

```text
解码图像 → 模型约定的采样/像素转换/缩放
         → 可选去噪与面部/手部/身体特征提取
         → 连续序列或模型要求的输入
         → 手语模型 + 对应时序解码器
         → 带时间范围的识别更新
```

- 保留面部信息接入位置；究竟是独立人脸检测、面部关键点还是端到端视频模型，由模型契约决定，不要求所有模型都接受“人脸框 + 视频”。
- 区分单动作分类与连续手语识别。若训练阶段只得到单动作模型，产品能力标记为独立动作识别，不直接声称可以自由连续翻译。
- 去噪不是默认必选项。双边滤波可能影响手指细节并增加耗时，只有训练预处理一致且对验证结果有益才启用。
- TFLite / ONNX Runtime 根据实际模型及算子支持选定；GPU 加速须实测，不能保证所有算子都落在 GPU。
- 预处理作为一个有界执行阶段，推理实例按后端要求固定线程/上下文；不为每个小步骤创建无限协程。
- PC 与 Android 使用相同样本比对预处理张量和识别结果；差异超过既定容差时阻止发布。

### 2.4 Sentence Manager 与 LLM — 连续表达、自动分段及选定语言输出

#### 2.4.1 模型、大模型与 App 的责任

| 部分 | 负责 | 不负责 |
|---|---|---|
| 手语模型及其时序解码器 | 判断动作内容，提供词序列/句子、时间范围和稳定内容；按训练算法去除解码中的重复标签 | 手机权限、语音是否已播、队列调度 |
| 自动边界判断（模型内或配套模块） | 根据经过验证的时序信号确定可提交的表达边界，给出媒体截止点及可靠性信息 | 用任意静默时长或标点猜测视频边界、要求用户逐句操作 |
| App `SentenceManager` | 维护句子编号、版本、时间范围；处理重叠窗口、自动确认、中断和过期回调，持续接收后续表达 | 凭空猜测漏掉的动作 |
| LLM | 对已确认内容进行受限文字整理，并翻译成选定语言；文本拆分/合并策略预留于 §2.4.8 | 单凭文字倒推视频边界、判断是否已播报、补全未识别出的事实 |
| App `TtsManager` | 保证同一句每种语言自动播报不重复，处理顺序、语言和中断 | 从视频推断句子边界 |

模型内的重复标签消除与 App 的播报去重是两件事。用户做了两次相同表达，应形成两个不同句子并允许各自播报。以下“确认”默认指系统确认内容可提交，不是让用户每句操作；“句子/段”指带来源时间范围的处理单元，不要求用户刻意停顿或按固定长度表达。

#### 2.4.2 连续自动分段方案

```text
每段独立维护状态，采集与后续动作识别持续运行：
DRAFT（识别草稿，可反复修订）
    ├─ 经验证的自动边界信号 → FINALIZING（后台等待句尾处理完成）
    │      ├─ 截止点所需推理完成，边界与内容可靠 → FINAL
    │      └─ 收尾超时/内容不确定 → NEEDS_CONFIRMATION
    ├─ 内容缺失/低置信度/边界不明确 → NEEDS_CONFIRMATION
    │      ├─ 用户自愿核对或修改并确认 → FINAL
    │      └─ 用户放弃 → DISCARDED
    └─ 断流/必需帧丢失/过载 → INTERRUPTED，不自动播报

FINAL → 语言处理 → READY 或 NEEDS_CONFIRMATION → 字幕与 TTS
前段 FINALIZING / 语言处理 / 播报时，后段可处于 DRAFT
```

实施细则：

1. 一个会话使用 `sessionId`；每个句子使用唯一 `segmentId`，草稿修改只增加 `revision`，不创建新句子。
2. 帧与识别更新携带 `streamGeneration`、`sequenceEpoch`、媒体起止时间。重叠窗口更新对应段草稿，不把每个窗口的文本直接追加成新句子；段状态不是控制整个输入管线暂停的全局状态。
3. 自动边界可来自手语模型或配套时序模块。自然停顿、动作转换、模型结束信号等只是待验证的证据，不预设固定 1.5 秒无新文字就结束，也不能靠大模型补一个句号视为边界已确认。具体算法与阈值随模型验证确定；能力不足则继续训练与联调，不用逐句操作替代。
4. 有边界信号后进入 FINALIZING，记录信号到达的手机单调时刻，并按 ModelSpec 取得来源媒体截止点 `cutoffPtsUs` 及必需的后续上下文范围；不能立即冻结当时最新草稿。边界若来自手机时钟，须经已验证的时钟映射转换，不得直接作为相机媒体时间。
5. 等待覆盖截止点及必要上下文的推理完成；窗口尾部不足时只用已验证的结束处理，不任意补零或忽略句尾。收尾等待初始上限 2 秒，超时仅将受影响段标为待确认/可能不完整，不自动提交旧草稿，也不让用户等到收尾完成才继续表达。此时限与 FINAL 后语言处理期限分开统计。
6. 句尾处理期间继续接收后续帧并推进连续识别；各段可同时处于不同处理阶段，不代表对同一推理实例发起并发调用。原始帧只保留 ModelSpec 必需窗口，不为等待 LLM 或 TTS 累积整段视频；帧、待收尾段与文本均受各自预算约束，文本与段数预算待 §2.4.8 确定。
7. 若模型提供 token（词或子词）时间区间，按时间对齐与稳定性规则提交；只有整句假设的模型，适配器也必须证明能在连续输入下确定各段归属、保留跨边界上下文并避免漏动作。做不到时不作为连续翻译发布模型，不能通过禁止输入下一句或要求停顿来绕过。
8. 各段来源范围采用前闭后开区间 `[startPtsUs, endPtsUs)`，最终边界明确后按时间归属内容，避免边界点重复消费。推理窗口可跨边界共享上下文，但同一动作内容只能被正式提交一次；后段推理不能改写已冻结前段。健康的自然换段不清空整个识别状态或增加 `sequenceEpoch`，只有断流、缺帧、过载等使连续性失效时才重置；已冻结句子的语言任务与当前草稿分别管理。
9. 边界信号不是无条件确认：同时检查缺帧、拒识及内容可靠性。边界不明确时保留相关范围为待核对，不把猜测的切点当成已消费事实；从后续可独立确定的边界继续处理可靠内容，不与可疑范围重叠提交。待核对项不弹出强制模态窗口、不阻塞后续表达，也不能无限堆积；容量与超限策略列入 §2.4.8 的发布前待定项。
10. FINAL 后冻结原文和来源范围；收尾超时或转待核对时也封存该次修订，迟到推理不能覆盖它，更不能覆盖用户已核对/修改的文本。修改已确认内容必须是显式纠错，不在已经播报后无提示替换含义。
11. LLM 只处理 FINAL 文本，不处理每次草稿更新；同一 `(sessionId, segmentId, revision, language)` 只保留一个有效结果。语言处理发现语义风险时，该语言结果转待确认，不自动播出新的可疑措辞；其余可独立处理的段继续运行。
12. 断线、停止或设置变更使尚未生效的请求过期时，即使底层调用后来返回也丢弃结果。可选核对后的旧段可更新字幕，但不能在后段播出后突然自动补读；需要声音时由用户显式选择重播。

示例：

| 输入事件 | App 状态 | 字幕与声音 |
|---|---|---|
| 模型输出“我需要” | 句子 A，草稿 v1 | 中文被选中时可显示原始草稿，无声音 |
| 同一动作窗口更新为“我需要帮助” | 句子 A，草稿 v2 | 替换草稿，不新加一句 |
| 系统检测到经验证的表达边界 | 句子 A，FINALIZING | 后台收尾，不要求点击或停止表达 |
| 用户紧接着继续表达 | 后段 B 开始识别，A 可仍在收尾 | 持续接收动作，不等上一句翻译或播报 |
| A 的截止范围及必要上下文处理完成，内容可靠 | 句子 A，FINAL | 整理后显示，按表达顺序播报一次 |
| B 恰好也表达“我需要帮助” | 独立句子 B | 不因文字相同去重，确认后按序播报 |

未选中文时不把原始中文草稿当作选定语言译文显示，界面显示“正在识别”；待核对内容可由用户自愿展开查看来源文本，不能用错误语言冒充翻译。

#### 2.4.3 数据契约

下列是领域接口示意，不是对 SDK 回调字段的扩充。

```kotlin
@JvmInline
value class LangCode(val tag: String)

data class ConfirmedSentence(
    val sessionId: String,
    val streamGeneration: Long,
    val sequenceEpoch: Long,
    val segmentId: String,
    val revision: Int,
    val startPtsUs: Long,
    val endPtsUs: Long,
    val rawChinese: String,
    val confidence: Float?,
    val userConfirmed: Boolean
)

data class OutputPreferences(
    val selectedLanguages: List<LangCode>,
    val spokenLanguages: List<LangCode>,
    val backend: LanguageBackend,
    val revision: Long
)

enum class LanguageBackend { LOCAL, CLOUD }
enum class OutputSource { LOCAL, CLOUD, FALLBACK }
enum class OutputStatus { READY, NEEDS_CONFIRMATION, UNAVAILABLE }

data class LanguageResult(
    val sessionId: String,
    val streamGeneration: Long,
    val sequenceEpoch: Long,
    val segmentId: String,
    val sentenceRevision: Int,
    val settingsRevision: Long,
    val language: LangCode,
    val text: String?,
    val status: OutputStatus,
    val source: OutputSource,
    val elapsedMs: Long
)

interface LanguageProcessor {
    fun process(
        sentence: ConfirmedSentence,
        preferences: OutputPreferences
    ): kotlinx.coroutines.flow.Flow<LanguageResult>
}
```

`confidence=null` 表示模型没有可比较的置信度，不虚构分数；外部输入在进入领域层前校验。识别媒体时间用于对齐，`elapsedMs` 使用手机单调时钟统计并包含相关排队等待。`userConfirmed` 仅记录是否经过用户自愿核对，系统自动确认可以为 `false`，不作为正常播报必须为真的条件；`startPtsUs` / `endPtsUs` 遵守前闭后开区间约定。

#### 2.4.4 用户语言选择与设置生效

- 默认 `selectedLanguages=[zh-CN]`、`spokenLanguages=[zh-CN]`，用户可改为一种或多种支持的语言，或关闭声音；语音语言必须属于选定字幕语言。
- 仅中文：只整理中文，不生成任何外语，不预加载无关翻译任务。
- 仅英文等其他语言：内部保留中文识别依据，仅生成并输出该目标语言；不强制额外播报中文。
- 多语言：按用户排列的优先顺序处理，单个语言就绪即可交付，不等待全部语言完成。低优先级任务不能无限阻塞后续主要输出，受同一句总处理期限限制。
- 本地仅保留一个语言模型执行任务，复用模型；同一句的语言按顺序处理，不能为每种语言同时加载一份大模型。
- 设置通过 DataStore/StateFlow 等可观察状态管理，不用首次注入时固定的语言列表。每个句子提交时取得设置快照；变更设置取消尚未完成的旧设置任务，拒绝旧版本结果，并清空尚未开始的旧语音任务。
- 设置变更不自动重播历史句子；已显示内容不偷偷替换，用户可显式要求重新处理。普通语言切换允许当前正在播的那一句结束，用户关闭声音则立即停止。
- 无法处理目标语言时显示该语言不可用的状态，不把原始中文标成英文结果，也不偷偷切换为用户未选的语言。

#### 2.4.5 LLM 忠实性限制

系统提示和应用校验共同执行以下规则：

- 只调整已有内容的语序、必要虚词和标点；不得新增人物、地点、时间、数量、因果、意图或承诺。
- 必须保留否定、疑问、数字、单位、专名和有意重复；不能把“不需要”整理成“需要”，也不能擅自补回模型没识别出的“不”。
- 缺失信息、未知标签及低置信度不能靠上下文猜完；转待确认。仅供衔接的上下文来自已确认句子，并有长度上限，不作为填补事实的依据。
- 识别文本只是待处理数据，其中出现“忽略规则”等内容也不作为指令；语言处理不调用外部工具或执行文本中的操作。
- 使用结构化结果并检查语言、状态、长度和必要字段；数字、否定等可做差异检查，但此类检查不构成跨语言语义正确性的证明。
- 模型标记有歧义、应用检测到关键语义变化或输出无法校验时，不自动 TTS；要求用户确认或保留来源文本。
- 发布前用遗漏否定、数量、专名、重复动作及低置信度样本测试误改率。提示词不能保证零幻觉，文档不承诺模型会自动修复识别错误。

> 本节涉及本地引擎与本地降级的条款冻结（文字保留，不实现）；"云端失败后
> 降级本地"路径按"直接报告未完成"执行。

- 本地引擎候选为 MediaPipe LLM / llama.cpp，具体模型、语言覆盖、内存和耗时在目标机上验证；不把某个引擎名称当作所有手机可运行的保证。
- 云端后端仅接收用户允许发送的文本，不上传相机帧。开发调试凭据不进入日志或版本库；发布包不能内置可被所有安装者提取复用的服务端主密钥，凭据交付方案在启用云端前单独验收。
- 本地每句处理期限初始 3 秒，云端初始 10 秒，从句子 FINAL 开始计入排队、中文整理、所选语言翻译及网络等待；这些是超时保护，不是正常性能目标。
- 多语言按优先级共享该句期限，已返回语言不回滚，超时的语言标记不可用；不为每个语言无限延长整句等待。
- 本地中文整理超时/不可用：若中文已选择且来源文本已可靠确认，可显示原始拼接文本并标注“未润色”；有歧义则只显示待确认状态，不自动播报。
- 外语不可用时不能拿中文冒充该语言译文；已选择中文时中文仍可独立输出。
- 云端失败后，仅在本地模型就绪且剩余期限允许时降级到本地，否则直接报告未完成；不得先等满云端超时再无限追加本地等待。

#### 2.4.7 相机 Wi-Fi 与可选公网请求

```text
GO 3S 热点 ──Wi-Fi── 手机：相机控制与视频数据
                         │
                         ├─ 本地识别 + 本地语言处理：不需要互联网
                         └─ 用户启用云端时：蜂窝网络 → 文本 API
```

相机热点用于局域网传输，不要求它提供互联网。这与手机能否使用蜂窝访问云端是两个问题；仅使用本地功能时，不申请蜂窝网络来“补足”相机连接。

启用云端时：

1. 通过 `requestNetwork` 请求具有 `TRANSPORT_CELLULAR` 与互联网能力的网络，等待回调并处理不可用/丢失，检查实际可达性；不靠轮询 `allNetworks` 激活网络。
2. OkHttp 同时使用蜂窝 `Network.socketFactory` 和委托给该 `Network.getAllByName(host)` 的 DNS，避免域名查询仍走相机热点。
3. HTTP 客户端按有效网络复用，网络丢失后取消相关请求并废弃旧客户端。不要每句新建连接池，也不把进程整体改绑蜂窝而破坏相机连接。
4. 默认 HTTPS 与正常证书校验；云端域名不需要相机本地明文网络的例外。相机 SDK 若需要明文通信，只给实际必要范围配置，不全局放开。官方 Demo 的 `network_security_config.xml` 提供参考实现：`domain-config` 仅放行 `192.168.42.1` 与 `aware.insta360.camera`，`base-config` 禁止明文；按此抄写并在真机验证生效。
5. 双网可用性依赖手机、运营商和用户设置，不保证所有设备能并用；失败时保持相机连接并按所选语言降级。
6. 用户退出云端或结束会话时注销蜂窝请求。费用与文本离机处理在启用前明确告知。

| 待核对与会话文本缓存 | 待核对条目数、总字节数、保留方式和超限提示；不依赖用户立即处理来回收容量，不擅自开启历史持久化 |
| 大模型完整输入预算 | 系统提示、当前已确认内容、衔接上下文、结构化格式和预留输出共同占用的上下文预算，按该模型的 token 计算；token 是模型分词后的单位，不等于一个汉字 |

### 2.5 TTS Engine — App 管理播报

#### 2.5.1 离线准备

- 不假设系统已装中文或其他语言的离线语音。
- 初始化后检查 `isLanguageAvailable` / `setLanguage` 的结果，区分 `LANG_MISSING_DATA`、`LANG_NOT_SUPPORTED` 和引擎失败。
- 对用户选定的播报语言选择 `isNetworkConnectionRequired=false` 的可用 Voice，检查设置结果；需要下载时提示用户先在可上网状态安装语音数据。
- 未准备好的语言仅显示字幕，明确标记语音不可用；不替用户选择其他语言或自动改用联网语音。
- 飞行模式下单独开启相机所需 Wi-Fi/BLE，或关闭移动数据进行验收，验证所选语音确实离线可播。

#### 2.5.2 顺序、去重与中断

- 只自动播报已确认且通过语言处理检查的 READY 文本；DRAFT、FINALIZING、NEEDS_CONFIRMATION、INTERRUPTED 不播报。
- 自动播报键为 `(sessionId, segmentId, language)`，不是“5 秒内文字相同”。同一句的多次回调不重复排队；用户重新说同一句话有新 `segmentId`，可以再次播出。
- 模型负责动作/文本判断，TtsManager 负责播报状态；大模型和手语模型均不能替代 App 的队列管理。
- App 自管一个串行队列：一次只向系统引擎提交一条，当前任务终结后再切语言和提交下一条，防止并发修改引擎语言。
- 每次实际提交生成唯一 `utteranceId`，重播也使用新 ID。提交前登记当前任务；`speak()` 同步返回 ERROR、`onDone`、`onError`、`onStop` 都进入同一幂等终结流程，只处理匹配当前 ID 的事件。
- 主动停止立即使当前任务终结并按操作清理队列，不等待 `onStop` 才解除占用；迟到的旧回调不能推进新任务。设置有限的引擎响应看门狗，初始 60 秒，超时调用停止并标记失败；调整上限需覆盖允许的文本长度与语速。
- 按来源媒体时间确定的表达顺序、句内用户语言优先级播报，不按推理/语言回调完成顺序抢播。若更早段仍收尾或处理，等待其就绪或到达相应期限；已转待核对、中断、不可用的段跳过自动播报，不等待用户操作。某段或语言错过播报顺序后可补字幕，但不在下一句后突然补读旧句。
- 初始最多缓存 3 个待播句子；进入待播后超过 5 秒仍未开始，转为字幕保留并标注“未播报”，不悄悄删除内容。用户可点击重播；容量和期限通过实际语速测试调整。语音排队不暂停相机或要求用户等播完再表达。
- 正常新句不使用 `QUEUE_FLUSH` 打断上一句。只有用户明确点击停止、关闭声音或开始指定重播时才停止当前声音并按操作清队列。
- 请求并处理音频焦点，包括请求失败、暂时失焦、永久失焦和释放；Android 15+ 且 target≥35 时，顶层应用或运行中的前台服务条件必须满足。“降低其他声音”不是 App 可强制保证的行为。
- TTS 错误或中途失焦导致播报中断时标注状态，不自动无限重播；进程重启不恢复旧自动播报队列。

### 2.6 Cache Manager — 文本历史与隐私

- 成品视频帧和编码数据仅短暂驻留内存；不截图、不写图片/视频缓存。日志中不记录帧内容、热点密码、API 凭据或整段敏感对话。
- 文本缓存是默认开启的核心功能（对应原始需求）。首次使用时告知缓存内容、保留期限和删除方法；用户可关闭，关闭后停止写入新记录，已存记录由用户选择删除或保留。视频采集授权与文本缓存互相独立，互不连带。
- 使用 App 私有目录的 Room，保存 `sessionId`、`segmentId`、确认原文、用户所选语言结果、状态、时间、可用置信度、模型版本和处理来源；未完成或有歧义的结果不得伪装成正常译文。
- 按 `(sessionId, segmentId)` 更新记录，语言结果按语言键合并，不把一个句子的每个草稿版本都存成新历史。
- 历史保留最近 90 天且不超过 10000 条，任一条件超限就清理；支持按句、按会话及全部删除。
- 导出 JSON/CSV 必须用户主动触发，使用系统文件选择/分享机制，不常驻公共目录。提示导出后的文件由接收方管理；CSV 导出处理可能被表格软件当公式的前缀。
- 禁止会话数据库、模型凭据和训练数据进入未声明的系统备份；检查 SDK 自身日志、缓存和崩溃采集，不仅检查 App 自己的写文件代码。

### 2.7 UI Alert — 无视频画面的状态反馈

界面包含会话开始/停止、连接与模型状态、选定语言字幕、可选的疑义核对/纠错入口、语言设置、语音准备提示及历史记录；不提供逐句结束按钮，不弹出要求用户先确认才能继续表达的对话框。自动收尾在后台进行，只显示必要状态；训练版额外显示采集授权、连接状态、采样规格、吞吐、缓冲占用与缺帧统计，不显示视频。

遵守系统勿扰和震动设置；不能仅靠 `getRingerMode()` 判断全部勿扰策略。实现震动时按 API 的停顿/震动时长语义构造效果并实测，不直接把普通时长列表当成必然相同的震动模式。

### 2.8 USB Bridge — 仅训练版的 PC 采集通道

#### 2.8.1 连接方向

采用手机监听、PC 主动连接：

```text
手机 training App：ServerSocket 绑定 127.0.0.1:9999
        ▲
        │ adb forward 建立的端口通道
        │
PC：Python 客户端连接本机 127.0.0.1:9999

连接建立后：相机 → 手机解码 → 同一条 TCP 连接 → PC 接收并保存/训练
```

在 PC 执行：

```bash
adb -s DEVICE_SERIAL forward tcp:9999 tcp:9999
```

然后在手机训练版点击“开始采集服务”，PC 客户端连接本机端口。TCP 建立后可双向传输；使用 forward 不限制帧只能从 PC 发往手机。任务结束关闭 App 采集服务并在 PC 撤销映射：

```bash
adb -s DEVICE_SERIAL forward --remove tcp:9999
```

多手机时各自指定设备序列号与不同 PC 端口；9999 只是本方案的默认值。只有改成 PC 监听、手机主动连接时才采用 reverse，本方案不混用两者。

#### 2.8.2 数据与背压协议

- 手机只监听回环地址，不监听 `0.0.0.0` 或相机 Wi-Fi 地址；仅在用户打开训练采集时启动。回环地址不是对同一手机其他应用的访问隔离，仍须认证。
- 单客户端；每次训练会话使用临时配对令牌，由训练版显示供用户输入可信 PC，不在日志打印令牌。ADB 调试只对可信 PC 授权，训练完成关闭调试/撤销不需要的授权。
- PC 首条消息为 AUTH，手机接受连接后 5 秒内必须完成整个认证；认证前不发送任何帧或会话素材，认证失败/超时关闭该连接并恢复接受新连接。
- TCP 是字节流，不能假设一次 read 就是一帧。消息使用 4 字节大端 JSON 头长度、UTF-8 JSON 头和头中声明长度的 payload；接收端循环读满并校验长度，异常则结束连接。
- 收到一条消息首字节后，2 秒内须读满该消息；使用整条消息的单调时钟截止时间，不能每收到一小片就无限续期。双方空闲时每 2 秒发送心跳，6 秒未收到任何完整有效消息即断开；认证与读超时均释放单客户端槽位。
- 消息区分认证、心跳、会话配置、帧、缺帧/中断事件和结束。帧头至少包括协议版本、`sessionId`、数据代次、帧序号、媒体时间戳与单位、尺寸、像素格式、预处理版本和 payload 长度；控制消息不要求虚构图像字段。
- JSON 头初始上限 16 KiB，图像 payload 初始上限 32 MiB，控制消息 payload 上限 64 KiB；实际传输尺寸在建立会话时协商，不超过上限。紧凑像素帧核对声明长度与尺寸，拒绝越界或未知格式。
- 初版传紧凑 I420 或 RGB 原始像素及元数据，格式在会话配置中固定；不默认把 JPEG 压缩伪装成纯像素转换。若以后确需 JPEG 减少 USB 流量，作为显式数据集版本评估压缩对识别的影响。
- 采集线程与 PC 训练计算分离。PC 接收器负责快速保存授权样本，训练从数据集读取，不能因 GPU 训练一批数据就暂停接收。
- 训练像素发送池默认预算 **128 MiB**，在目标手机整机内存与持续压力测试通过后可选 **256 MiB**，内存不足可选 64 MiB 或不支持当前规格；由训练配置在采集段开始前确定并记录，不运行中自动扩容。预算覆盖正在转换的目标帧、待发送帧、在途发送帧、池中空闲块及相关元数据，不为同一帧保留额外未计费副本。解码器内部内存仍需另计；不能长期扣住 codec 的 Image 来充当发送缓存。
- 缓冲目标为最多约 **2 秒采集数据**，帧数上限按 `ceil(captureFps × 2)` 与扣除开销后的预算可容纳帧数取较小值；转换和发送中的帧也占名额，分配前预留预算。帧进入发送阶段到完整写出初始不超过 2 秒，以手机单调时钟检查最老帧，不能因不断写出少量字节而续期。容量允许短时积压，不承诺所有规格都能缓存满 2 秒。
- 入队将超过帧数或字节上限、最老帧超时，或写入连续 1 秒没有进展，任一发生均中断当前采集段并结束该连接；不阻塞相机回调、不覆盖旧帧后假装连续、不静默丢掉新帧。即使每次写入都能前进，持续吞吐不足最终触及容量/年龄上限也执行同一规则，而不是只依赖单次写阻塞超时。
- 中断时停止接纳该段新帧，关闭 socket 解除阻塞，按 §2.1.3 等待转换/发送任务退出后释放缓冲；手机显示采集不完整及原因。中断事件只能尽力发送，不能靠它一定送达才让 PC 判定失败；PC 未收到有效结束事件即将该段标记为不完整。恢复需新开采集段，不能把未发送积压拼到新段。
- 发生编码恢复、帧丢失或重连时记录中断；PC 不将中断前后的帧直接拼成连续训练样本。接收不到有效结束事件，或在此之前心跳/连接异常，PC 将当前样本标记为不完整；收到并验证正常结束后的连接关闭不撤销已完成状态。
- 用户正常停止采集时，先停止接纳新帧，固定最后接纳的完整帧范围；只允许既有转换/发送任务在停止后的初始 2 秒内收尾，且不重置各帧原有年龄与读写截止。全部完成后按同一串行写通道发送 END，声明结束状态、末帧序号及有效媒体范围，再关闭连接；PC 核对序号连续性、声明范围及已保存内容后才标记完成。未确认完整的尾部按 §2.2.1 丢弃，不宣称覆盖用户停止的精确瞬间；任一丢失、错误或收尾超时均按不完整结束，不能发成功 END。
- 先测真实 USB 带宽、像素转换及磁盘写入速度，并显示缓存占用、最老帧年龄、输入/发送速率；不承诺任意分辨率都能满帧传输。短时波动可在验证后增加缓存，持续发送不足须优化接收/写盘或调整采集规格；需要降规格时记录新 `CaptureSpec` 并开新采集段，不静默丢帧后仍标称原帧率。

容量估算示例（仅为计算示例，**不是指定相机规格或模型帧率**）：

| 紧凑像素规格 | 单帧大小 | 128 MiB 的理论帧数上限 | 按示例 30fps 折算 |
|---|---|---|---|
| 1920×1080 I420 | 约 2.97 MiB | 约 43 帧 | 约 1.43 秒 |
| 1920×1080 RGB888 | 约 5.93 MiB | 约 21 帧 | 约 0.70 秒 |

上述只计算像素，实际还须扣除元数据与其他池内开销；256 MiB 档可增加容量，但仍受 2 秒目标及帧年龄限制。缓存等待、单次写入无进展、接收端整条消息的 2 秒读截止是不同约束，扩大缓冲不取消连接存活与读写超时检查。

#### 2.8.3 采集授权与素材管理

- 训练版启动服务与 PC 保存素材是显式操作，界面持续显示采集中；受采集者应知晓用途和保存范围。
- 素材只落到 PC 用户指定目录，手机不提供“公共目录写帧 + adb pull”路径。
- 记录匿名化受试者编号、授权记录关联、相机/固件、机位、采样配置、模型与预处理版本；标签记录开始/结束与文本，不把模型猜测直接当人工真值。
- 数据集按受试者/会话划分训练、验证和测试，避免同一段视频的相邻窗口分到训练与测试而虚高准确率。
- 约定访问者、保留期限和删除范围，采集前填写；未明确授权或期限不开始持久化。手机“停止”不能远程保证 PC 已有副本被删除，PC 删除需单独执行并记录。

## 3. 开发环境与技术栈

### 3.1 虚拟环境的适用范围

**PC 训练用 Python 虚拟环境，Android 用项目级构建工具隔离；二者不是同一种环境。**

| 部分 | 隔离方式 | 解决的问题 |
|---|---|---|
| PC 训练/采集脚本 | 每个项目独立 `uv` 管理的 `.venv`，锁定 Python 与训练依赖版本 | 不污染系统 Python，不与其他训练项目冲突 |
| Android App | 项目 Gradle Wrapper、指定 JDK、固定 SDK/NDK 与版本目录 | 构建工具版本可重复，不依赖机器上的任意全局 Gradle |
| GPU 训练 | 记录显卡驱动、CUDA/框架兼容版本 | `.venv` 不隔离宿主驱动，不能靠它解决所有 GPU 不兼容 |
| 手机运行 | 真实 Android 手机安装 APK | Python 虚拟环境不能替代真机的 BLE/Wi-Fi、解码器和 TTS 验证 |

PC 训练目录创建后，在该目录统一使用 `uv` 建立环境与依赖（不使用 pip/conda/poetry）；本次只修改设计，不安装工具或创建实际环境：

```bash
uv init                          # 生成 pyproject.toml，并创建 .venv
uv add <训练框架及依赖>          # 依赖在训练框架选定并验证后加入
uv run python <脚本>             # uv run 自动使用 .venv，无需 source activate
```

依赖由 `uv add` 写入 `pyproject.toml` 并锁定在 `uv.lock`，不手写 `requirements.txt`（若目标环境只认 `requirements.txt`，用 `uv export` 生成而非手动维护）。训练框架选定并验证后再加入依赖，不假定现在已有这些依赖。Android 的 JDK 路径由项目/IDE 指定，使用仓库内 Wrapper 命令构建，不把 Android 依赖放进 Python 虚拟环境。

### 3.2 技术选择与版本门槛

| 层 | 选择 | 说明 |
|---|---|---|
| 语言/UI | Kotlin + Jetpack Compose | 仅状态、字幕和控制，无视频播放器 |
| 架构 | 前台会话服务 + MVVM/Repository + StateFlow | 服务拥有连接和工作任务，界面观察状态 |
| DI/设置 | Hilt；DataStore 或等价可观察设置 | 设置不是一次性注入快照 |
| Android 版本 | minSdk 29；compileSdk/targetSdk 35 | 官方 Demo 2.1.5 实测值（minSdk 29 应与 `WifiNetworkSpecifier` 需 API 29+ 有关，覆盖 Android 10+）；是否升 36 在 AAR 实测后再定 |
| Android 构建基线 | AGP 8.7.3 + Gradle Wrapper 8.11.1 + JDK 17 | Demo 2.1.5 `libs.versions.toml` 与 wrapper 锁定的已验证组合；先跑通该组合再考虑升级 |
| Android Studio | Ladybug 2024.2.1 及以上（本地已装 Quail 4 Patch 1） | SDK 推荐环境；构建工具由项目锁定，不随 IDE 自动升级 |
| Kotlin | 2.3.20 | Demo 2.1.5 锁定值；KSP、Hilt 与 SDK 仍须联合验证 |
| ABI | 仅 arm64-v8a | Demo `abiFilters` 限定；x86 模拟器无法加载 SDK native 库，取流验证只能真机 |
| 相机 SDK | `com.arashivision.sdk:sdk-camera:2.1.5`（+ `sdk-media:2.1.5`） | Demo 锁定版本，不混用 1.x；Media SDK 仅在实际依赖要求下引入 |
| 解码/像素处理 | MediaCodec + 经布局验证的转换实现，如 libyuv | OpenCV 仅在模型预处理确需时引入 |
| 手语推理 | TFLite 或 ONNX Runtime | 根据训练模型、算子、后端实测决定 |
| 语言处理 | 本地模型优先；可选文本云端后端 | 按用户选定语言生成 |
| 语音 | Android TextToSpeech | 所选离线 Voice 先检查再使用 |
| 文本历史 | Room | 按授权保存，无视频表或帧缓存 |
| 异步 | Coroutines + 有界 Channel + Flow | 有资源所有权和过载规则 |
| PC 训练 | Python（`uv` 管理的 `.venv`）+ 后续选定的训练框架 | 固定依赖及记录训练运行环境 |

虚拟环境不能把本来不兼容的 AGP/Kotlin/SDK 组合变成兼容。构建验收必须同时覆盖目标 SDK、NDK/native 库、模型运行时、Hilt/KSP 和两个构建变体。

另外：Demo `settings.gradle.kts` 内置 Insta360 Maven 仓库的 guest 凭据（`insta360guest`），依赖 `com.arashivision.sdk:sdk-camera:2.1.5` / `sdk-media:2.1.5` 可直接解析。guest 凭据属于 Demo 分发物，本项目仓库不提交任何凭据，构建时从本地环境注入；正式发布前评估是否申请独立凭据。

## 5. 会话时序

```text
App 初始化 SDK、设置与 DI
    → 用户选择语言/运行版功能并点击开始
    → 权限与设备状态检查
    → 前台服务持有会话
    → BLE 发现、读取相机热点 → 系统连接 Wi-Fi
    → 进程绑定相机网络 → 相机连接/授权/必要激活
    → loadJson / 编码能力查询 / 注册取流监听
    → startStream → 实际参数 + 参数集 + 随机访问关键帧
    → 无显示 Surface 解码 → 布局读取与基础转换
        ├─ training：用户授权采集 → PC forward 连接 → 有界发送缓冲 → PC 保存
        └─ production：按 ModelSpec 采样 → 连续识别 → 自动确定表达边界
                        → 各段后台收尾/确认 → 所选语言处理 → 字幕和受控播报
                        （后续动作持续接收，不等待前段收尾、翻译或播报）
    → 用户停止 / 不可恢复错误 → 禁止新任务、取消并等待实际执行者退出
                             → 释放资源与网络解绑
```

模型、自动边界、语音等本地资源准备可与连接步骤并行，但只有所有必需条件满足后才宣告“正在识别”。视频数据来到并不代表模型、语音或云端已经可用。

## 6. 错误处理矩阵

| 场景 | 处理 |
|---|---|
| 权限拒绝/撤回、用户取消网络连接 | 不继续调用受限 API；结束本次启动/会话，提示原因及修复方式 |
| 授权拒绝、授权忙碌、激活失败 | 显示准确状态并停止后续取流准备，不假装已连接可用 |
| Wi-Fi 或相机连接中断 | 中断草稿，取消旧代次任务，按 5 次退避重新准备；失败后震动 |
| 相机低电 | 状态提示、限频震动，用户决定停止；设备停止供流再按断线处理 |
| 相机过热 | 停流并进入 PAUSED_HOT，冷却后由用户恢复，不自动反复重启 |
| 取流 5 秒无视频数据 | 检查网络和流状态，执行一次受限恢复；仍失败计入会话重试预算，避免无限循环 |
| 编码队列、聚合超限或损坏 | 按 §2.2 清空受影响编码/解码状态，请求参数与关键帧，标记时序中断 |
| 解码不兼容/参数变化 | 重新核验配置；不可读则提示设备/规格不支持，不按固定 NV12 强读 |
| 模型缺帧/过载 | 使未确认序列失效，旧推理返回不生效；持续发生暂停并提示换已验证配置 |
| 模型未安装、版本/输入不匹配、自动边界能力未就绪 | 禁止开始连续翻译，保留状态界面，不输出伪造结果或改用逐句按钮 |
| 低置信度/缺失关键信息/边界不可靠 | 仅草稿或待核对，禁止自动润色补事实及自动 TTS；不要求用户核对后才能继续，后续可靠且独立的段照常处理 |
| LLM 超时/输出不合约 | 按选定语言和剩余期限降级；风险文本转待确认，不凭流畅程度判成功 |
| 云端无公网、DNS/蜂窝丢失 | 相机连接保持不变；切就绪的本地处理或显示语言不可用 |
| TTS 缺少语音/初始化或播报失败 | 保留字幕并说明语音状态，提示准备离线语音，不自动切换联网引擎 |
| 文本历史写入失败 | 不影响实时字幕，提示本次未保存，不把视频写盘作为补偿 |
| USB 队列满/帧年龄超限/写入堵塞/PC 断开 | 结束当前采集连接，PC 标记样本不完整；释放前等待任务退出，不回退为公共目录存帧，不拼接新旧采集段 |
| 停止时原生任务尚未退出 | 保留仍在使用的输入和资源，阻止重叠启动；超时提示清理异常，独立资源照常清理，任务实际退出后再释放其资源 |
| 用户停止/进程被杀 | 停止不触发重连；下次打开显示已中断，不恢复旧自动播报 |

## 7. 延迟与质量指标

### 7.1 计时定义

| 指标 | 起点 → 终点 | 用途 |
|---|---|---|
| 手机取流处理 | 手机收到编码片段 → 对应模型输入准备完成 | 分析聚合、解码和预处理 |
| 模型增量延迟 | 该次窗口最后必需输入到达 → 草稿更新 | 区分计算慢与等待动作完成 |
| 自动确认等待 | 标注的表达边界 → 对应段 FINAL | 包含边界判断、必要后续上下文和句尾推理，不依赖人为点击 |
| 选定语言字幕延迟 | FINAL → 对应语言 READY 并显示 | 包括队列、整理、翻译与网络 |
| 语音首声延迟 | FINAL → 实际发声开始 | 包括语言处理、TTS 等待和启动 |
| 端到端延迟 | 参考录像/同步实验标注的表达边界 → 对应字幕或首声 | 对用户体验验收，不混用相机与手机未同步时钟 |

选择中文时只统计中文处理路径；选择其他语言或多语言时分别记录，不承诺免费增加语言数量而耗时不变。用户语言选择可以避免不需要的翻译，但不能消除模型识别和自动边界判断所需时间。持续表达按标注的各段边界统计，不把整个会话停止时刻当作唯一终点；无法可靠划分的样本计入边界失败/未输出统计。

### 7.2 目标与测量规则

- **连续自动确认路径的初始目标**：仅中文、本地处理，在指定手机与模型上，标注的表达边界到对应确认字幕的 p95 小于 2 秒；p95 表示 95% 的样本不超过该值。这是待验收目标，不是已保证能力。
- 验收不要求受试者逐句操作或等待播报完成；必须覆盖前段收尾、翻译和播报期间紧接着继续表达的情况，检查后段动作是否漏识、串句或重复消费。自愿核对/纠错单独记录，不把它替代正常自动确认路径的性能数据。
- 不预设 1.5 秒无文字自动结束，不假定本地大模型必在 500ms 内完成；按实际模块用时分配预算。
- 各语言字幕、首声、完整播报分别统计 p50/p95、超时率、拒识率、未播报率和过载中断次数；同时报告自动边界误切/漏切率，不能仅在成功输出样本上报告延迟而隐藏失败样本。
- 准确率需要按任务定义：单动作分类、连续词序列及句子语义分别评估；重点报告否定、数量、人名和有意重复是否保留。
- 采集规格、模型大小、功耗、温升、峰值内存与持续运行速度一起评估；降低输入规格只能使用重新验证过的 ModelSpec。

**P0 门禁实测记录（2026-09-22，Demo APK + GO 3S 固件 v9.0.59 + 小米手机/MIUI）**：

| 项 | 实测结果 |
|---|---|
| 连接流程 | 通过：BLE 扫描列表的 Wi-Fi 按钮（BLE→读热点→系统热点确认→绑网→connect）一次成功；首页"W-Fi 直连"入口要求手机已在相机网络，否则约 5 秒超时失败，错误码 **-214**（可映射为"未连接相机热点"提示） |
| 激活 | 相机已激活（`activate_time` 有值），无需再走激活流程 |
| 普通预览流 | H.264，30fps，主流 640×360 + 副流 640×480，约 4Mbps，无音频，带 gyro；**实际编码尺寸 640×384**（5:3 鱼眼，声明值≠实际值）；CSD 61 字节随流发送；开流后约 2 秒出图；渲染稳定 30fps |
| 高分辨率取流 | **可行**：`VIDEO_LIVE` 模式下主流跟随相机 `video_resolution` 设置，实测 3840×1920@30 开流成功（主流 4K + 副流 640×360 并行）。1080p 路线：设 `video_resolution` 为 1080p 档 + live 模式开流，**不需要真正推 RTMP**（开流与推流是独立步骤）。普通 `VIDEO_NORMAL` 预览才固定 640×360 |
| 公开 API 分辨率控制 | `startStream()` 无参；分辨率由模式与相机设置决定；`setVideoBitrate(Int)` 可调码率；`startLive(CameraLiveParams)` 可指定 w/h/fps/bitrate 但属 RTMP 推流路径 |
| 发热 | 取流期间电池温度 52→55°C 持续上升，过热管理列为实测项 |
| 时钟怪癖 | 直播开流瞬间出现 `Gyro timestamp ahead Frame timestamp` 告警，印证 §2.2.2 相机/手机时钟不可混用的设计 |
| 日志泄露佐证 | Demo 日志明文打印热点 SSID/密码（`wifi_info`）与完整 RTMP URL（含 stream key）——本项目日志脱敏规则（§2.1.1、§2.6）有官方反例佐证 |
| OEM 差异 | MIUI 冻结后台 Demo 进程（Greeze/adbd 拒绝 JDWP）实证，前台服务存活须在 P2 验证 |

## 9. 明确排除项

- 面向人的相机视频预览、播放器和双路显示渲染。
- 逐句完成/提交按钮、强制核对后才能继续表达的流程，以及以人工操作替代未验证的自动边界能力。
- 全景拼接、HDR、PureShot、Action Pod 自定义字幕屏。
- iOS/桌面端直接接相机的成品；PC 仅承担训练与开发工具角色。这是项目范围决定，不是断言厂商绝无其他平台 SDK。
- 纯 BLE 传视频、默认 RTMP 云端推流。
- 成品视频/帧落盘、截图、训练端口及训练采集入口。
- 用重新压缩视频代替模型所需像素转换。
- 用大模型替代 App 的连接管理、句子版本管理与语音队列。
- 取流失败后自动转“短录像再下载”或自动上传视频；这些改变实时性与隐私边界，不是本方案的静默降级。
- 把未经实测的模型、设备规格、吞吐或延迟标为已确认能力。
